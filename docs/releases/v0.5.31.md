# v0.5.31

> **读者 / Audience**：终端用户 · 插件与集成者 · 维护者（发行说明）

相对 [v0.5.30](./v0.5.30.md)：支持读图的模型终于能**看见工具读进来的那张图**；每张送进请求的图旁边多了一行句柄说明；切到纯文本模型时不再中途翻车。

Relative to [v0.5.30](./v0.5.30.md): vision-capable models can finally **see the image a read-image tool just produced**; every inlined image gains a handle line; and switching to a text-only model no longer breaks mid-turn.

### 新增

* **视觉工具结果带图贯通（tool result vision）**：`read_image` 之类工具产出的图片，现在能作为**工具结果的一部分**送回模型，而不只是用户消息里的图。Anthropic：`tool_result.content` 接受 `text | image` part 数组；Gemini：`functionResponse` 旁边挂同级的 `inlineData` + 句柄 part；OpenAI Responses：`function_call_output` 仍是字符串信封，像素另起一个 `user` 项的 `input_image`。
* **图片句柄文本（`requestImageHandleText`）**：每张内联进请求的图前，先给一行说明——文件名（有则带）、`attachment sha256:` 前 8 位、字节数、**本次请求实际发送的预览尺寸**（`{width}x{height}px`）。模型因此知道图被缩放过、格式与原始字节可能不同，不再凭空猜。
* **protocol 内容扩展**：`packages/protocol` 新增并导出 `requestImageHandleText` · `textOnlyImageText` · `projectImageContentForTextModel` · `projectImagesForTextModel`，把「图片→文本占位」的投影集中到一处，历史保持 append-only。
* **各 provider 适配**：`packages/llm` 的 anthropic / gemini / openai-compatible / openai-responses 四个适配器统一在图片块前插入句柄文本；`offloaded` 的图块跳过。

### 修复

* **纯文本模型不再硬失败**：`agent-loop` 在 `toLlmRequest` 与 token 估算两处按 `llmAllowsImage` 分流——路由不接受图像时，把历史里的图片块投影成 `textOnlyImageText` 占位（含 tool-role 结果），并且**不再传 `resolveImage`**；这样一次已经把图读完的会话切到纯文本模型，也不会在回合中途抛错。
* **`read_image` 提前拒绝并给指引**：路由不支持图像时立即返回 `the current model route does not declare image input; switch to an image-capable model to read images` —— 在碰文件系统 / 附件之前就退出，省掉一次无用的读盘。

### 其他变更

* 公开线目标 **`@xrkseek/harness-cli@0.5.31`**（接管 npm `@latest`）。
* Desktop 私有壳版本对齐 **0.5.31**；`apps/cli` / `apps/desktop` / `packages/sdk` 版本同步。

* 用支持视觉的模型（Anthropic / Gemini / OpenAI Responses）让助手读一张图：工具的 `tool_result` / `functionResponse` 里应带 `inlineData`（或 Responses 的后续 `input_image`）——模型能直接描述图中内容，而不是只看文本占位。

---

### Added

* **Vision tool results, end-to-end**: an image produced by a tool such as `read_image` now travels back to the model **as part of the tool result**, not only as a user-message image. Anthropic: `tool_result.content` accepts a `text | image` part array; Gemini: sibling `inlineData` + handle parts next to `functionResponse`; OpenAI Responses: `function_call_output` stays a string envelope and the pixels go onto a following `user` item's `input_image`.
* **Image handle text (`requestImageHandleText`)**: every inlined request image is preceded by a line naming the file (when present), the first 8 hex of `attachment sha256:`, the byte size, and the **exact preview size sent on this request** (`WxHpx`). The model thus knows the image may have been resized or re-encoded, and stops guessing.
* **Protocol content extensions**: `packages/protocol` adds and exports `requestImageHandleText` · `textOnlyImageText` · `projectImageContentForTextModel` · `projectImagesForTextModel`, centralizing the image→text projection while history stays append-only.
* **Provider adapters**: the anthropic / gemini / openai-compatible / openai-responses adapters in `packages/llm` all insert the handle text before an image block; `offloaded` image blocks are skipped.

### Fixed

* **Text-only models stop hard-failing**: `agent-loop` branches on `llmAllowsImage` in both `toLlmRequest` and token estimation — when the route cannot take images, retained image blocks (including tool-role results) are projected to `textOnlyImageText` placeholders and `resolveImage` is **no longer passed**. A session that already read an image can switch to a text-only model without erroring mid-turn.
* **`read_image` refuses early with guidance**: when the route lacks image input it returns `the current model route does not declare image input; switch to an image-capable model to read images` — before touching the filesystem or attachments, saving a pointless read.

## Verify

* With a vision-capable model (Anthropic / Gemini / OpenAI Responses), have the assistant read an image: the tool's `tool_result` / `functionResponse` should carry `inlineData` (or the following `input_image` on Responses) — the model describes what it sees instead of only a text placeholder.
* Every inlined image is preceded by `Image … (sha256:xxxxxxxx, N bytes); request preview WxHpx.`, with the size matching what actually went out.
* Switch the same session to a text-only model and send another turn: retained images become `[image omitted because this model accepts text only; attachment sha256:…]`, and the turn completes without error.
* Call `read_image` on a text-only route: you immediately get the "switch to an image-capable model" hint and no file read happens.
