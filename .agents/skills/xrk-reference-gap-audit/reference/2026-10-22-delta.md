### G4 · 跨进程写锁用 PID 判定"死锁持有者"并偷锁 → 会撕裂追加

> **状态（落地 · 保守）**：取消一切「按 PID 判死再偷锁」。`EEXIST` → `SessionsDirInUseError`。崩溃后的自动回收留给内核 mutex（未做）；操作员删锁文件。曾试 `net.Server` 同步 listen，`Atomics.wait` 会堵死事件循环 — 已撤回。

| 项 | 内容 |
| --- | --- |
| 对方出处 | DSH `feature/2026-08-31-cross-process-session-write-lease` |
| 对方结论 | POSIX 非阻塞 `flock(2)`、Windows 命名内核信号量（`CreateSemaphoreW`，count 1，由规范锁路径派生，**无文件系统足迹**、最后一个句柄关闭即销毁）。仲裁者必须在每个写进程之外。**明确拒绝**抢占卡住的持有者（"its resumed appends would tear compressed frames and seq contiguity"），也**不做 expiry 记账**——内核在描述符/句柄关闭时释放，崩溃持有者自然不阻塞后继 |
| 本仓证据 | `packages/core/session/src/store-lock.ts` 顶部注释：「Portable PID lockfile (no native flock addon) … **a crashed holder's stale file is stolen after the PID check fails**」。即本仓靠"PID 存活检查"判死，然后偷锁 |
| 风险 | PID 复用（Windows 上很常见）→ 判死错误 → 抢走一个**还活着**的持有者的锁 → 两个写者并发追加同一份日志。本仓所有会话在一个 SQLite 文件里（注释自陈），后果比 DSH 的单 JSONL 更集中 |
| 落点 | `packages/core/session/src/store-lock.ts`：Windows 分支改命名内核对象（CreateMutex/CreateSemaphore，靠句柄生命周期释放，取消"偷锁"）；POSIX 分支改 `flock` 语义（可用 addon 或 `open(O_EXCL)`+`/proc` 等更可靠的存活判定，但**必须取消仅凭 PID 存活就偷锁**） |
| 验收判据 | ① 双进程并发抢开同一 sessions 目录：后到者拿不到锁并抛既有错误（`SessionsDirInUseError` 一类），**不产生第二个写者**；② 持有者进程被 `taskkill /F` 后，后继进程能拿到锁（内核释放，非 PID 判定）；③ 单测覆盖"PID 复用/存活判定不确定"时**保守视为争用**（不偷）；④ 全仓不再出现"stolen" 路径的写锁抢占 |

### G6 · 提示符尾部缺 `promptTailGraceMs`（且该字段本仓完全没有）

> **状态（落地）**：`config.promptTailGraceMs` 默认 0；`session.ts` 仅在 `promptSeen && !promptTextSeen` 时加宽限期。

### G7 · `session.list` 组装无单调时钟时间片 → 大会话列表独占 Face 事件循环

### G8 · 打开历史会话时辅助 RPC 与主会话冷读争抢，且无"服务身份"可复用

DSH `bug-fix/2026-09-20-session-open-read-coordination`：`session.follow`、composer catalog 预热、带 Agent 参数的 RPC 会并发访问同一份冷日志；`skills/list` 自己请求完整 observation，`commands/list` / `goals/get` / `fileReferences/list` / `sessionReferenceResolver/candidates` 又会在参数解析中经 Agent 查找触发 resume —— 不等历史打开快照的辅助请求是在**抢**读取/解析/投影，而不是复用已完成结果。两个子问题：
- 复用已完成 observation 时，**服务容器可能为同一服务返回不同代理对象**，比较 `ctx.get('sessionPersistence')` 的引用会把同一服务误判成不同实例；但完全去掉身份比较也不安全（revision 只在同实例内可比）。修法＝服务自建 `Symbol('sessionPersistence')` 存于 `SessionPersistence.identity`，代理访问保留该值、替换实例得到不同值；缓存查 Session id 后**同时比 identity 与 `stat().revision`**。该身份仅进程内存在，不进 header / 事件 / 落盘文件。
- 辅助 RPC **等到当前会话的首次 open 成功**再发（复用既有 `sessions.using()` 于真实调用点，而不是只推迟预热钩子）；每个操作先检查目标已有 Client 绑定，避免后台预热重开已关闭会话。
本仓证据：`packages/server/face/src/context.ts:128` 有冷列表列，但无 prepared-observation 身份 Symbol；Client 侧 `sessions.using` 等价物零命中。
落点：`packages/core/session`（identity Symbol + prepared observation cache）、`packages/client/runtime` 各 RPC 调用点。
判据：打开 10 万事件历史会话时，`skills/list` / `commands/list` 等辅助 RPC 不再各自触发一次完整冷读（计数断言：同一 revision 只 prepare 一次）；用一个新 service 实例替换后旧缓存必须失效（Symbol 不同的用例）；代理返回不同对象但同一实例时**仍能**复用。
