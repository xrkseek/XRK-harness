## 1. 算法 / 性能：他们优秀、我们处理不好的

### A1 · 回合耗时的**关键路径归因** —— P0（本轮最值的一条）

**他们做得多好**：codex 新增 `codex-rs/utils/critical-path/`（提交 `af91f6ef2` + `082900149` 配套 `direct-tool-timing`）。它把一个回合的墙钟时间**独占归因**到关键依赖链上：

- `WorkKind` 六类（`lib.rs:12-32`）：`Inference` / `AutoReview` / `UserWait` / `Tools` / `Overhead` / `Unknown`。
- `PathDurations`（`lib.rs:68-75`）给出每类**独占**时长 —— 六项相加恒等于区间总长，不重叠、不遗漏。
- 三条关键算法（`lib.rs:91-150`）：
  - `work()`：把新段接在已有路径末端之后，**裁掉重叠**（`start = previous.max(start)`），空段忽略；
  - `join()`：汇合点**只保留真正释放等待方的那条分支**，且保留双方共同因果前缀（`latest()` 取后完成者）；
  - `durations()`：未记录的空隙一律算 `Overhead`；
  - `MAX_PATH_DEPTH = 16_384`，超深时把保留区间**折叠成 Unknown**，格式化与析构**绝不递归**链（`lib.rs:7`, `lib.rs:116-118`）。
- `CriticalPath` 用 `Arc<Node>` 共享前缀，`PartialEq` 比 **Arc 指针**而非内容（`lib.rs:33/48-52`）—— fork 成本 O(1)。

**我们处理不好**：本仓 `packages/stubs/xrk-session-stats/src/projection.ts:31-48` 的 `SessionStatsTotals` 是 `llmMs` / `toolMs` / `ttftMs` / `decodeMs` **各自累加**。`criticalPath` / `critical-path` / `exclusiveDuration` → **全仓零命中**。

后果：并行工具 + 等审批 + 模型推理混在一起时，`llmMs + toolMs` 会**大于**真实墙钟，或者说不清「用户等的那 40 秒是等人还是等机器」。本仓 `pendingCalls: Record<string, number>`（`:62`）已经记了每个工具调用的派发时刻，**原料齐了，缺的只是归因算法**。

**落点**：新增 `packages/stubs/xrk-session-stats/src/critical-path.ts`（TS 版：不可变节点 + `Map<id, Node>` 代 `Arc`，depth 上限同样折叠成 unknown）；`UserWait` 的边界从既有审批事件取。

**验收**：① 六类时长之和 == 区间总长（property test）；② 并行两个工具的回合，`tools` 不双计；③ 等用户批准的时长能单独出现在 `user_wait`；④ 深度超限降级为 `unknown` 且不递归。

### A2 · 流式工具参数：preparing 行显示不出字段 —— P1（**性能归因已撤回**）

**我们真正的成本在哪**（2026-10-22 micro-benchmark 实测，脚本曾落 `.tmp/bench-parse.mjs`）：

| 假设 | 实测 | 结论 |
| --- | --- | --- |
| ~~`argsRaw` 字符串拼接是 O(n²)~~ | 800 KB × 6 250 deltas = **0.2 ms** | **错**。V8 对 `acc = acc + p` 有 cons-string（rope）优化；DSH 的 Rust `String` 才需要担心 realloc。照抄其隐含假设 = 我的取证失误 |
| ~~每帧对未闭合 JSON 尝试 `JSON.parse` 会卡顿~~ | 总量：200 KB → 237 ms · 800 KB → 3.2 s（规模 ×2 耗时 ×4，确实 O(n²) 增长）。**但按帧拆开测**：`publish='animation-frame'` 把帧数钉在 **60 帧/秒 × 流时长**，与实际 provider 速率（200 KB ≈ 16 s）相除后 **per-frame P50 0.13 ms · P99 0.31 ms · max 6 ms · 0 帧超 16 ms**（@200 KB）；@800 KB P50 0.46 / P99 1.09 / max 8.0 / **0 帧掉帧**；1.6 MB 才出现 **1** 帧 21 ms | **也不是真凶。** 总量呈二次增长，但二次因子是「输入字节数」而非「帧数」—— 帧数与体积无关，故分摊到每帧是**线性 ~37 µs**。聚合 parse 成本在**墙钟**里完全不可见（provider 速率比本地 parse 慢一个数量级）。1 562 次抛异常是**浪费，但不可感知** |

**⇒ 结论：这条不是 P0，也不是性能问题。** 每帧 parse 的浪费在现实尺寸（50–200 KB）下是 sub-millisecond 级；为省它写一个增量 JSON 闭合扫描器是**负收益**（多一个缓存生命周期不变量、多 200 行、用户零感知）。**不要做「给 parse 加闭合闸门」这个修法。**

**hot path 定位**（亲自读过）：`packages/client/ui-tool/src/client/tool/models/diff-card-model.ts:135-148` →
`running` 且 `callView == null` 时走 `:146` `provisionalDiffFromArgs(toolNameOf(block), block.argsRaw)`，
其 `:37-42` 是 `if (argsRaw === '') return null` + `try { JSON.parse(argsRaw) } catch { return null }`。
该模块自己的注释（`:12-13`）已写明意图是 **"paint as soon as JSON closes"** —— 所以每帧尝试解析**未闭合**前缀纯属浪费，
连它自己的契约都不要求这么做。每帧调用者三处：`ToolDetails.tsx:43` · `GenericToolCard.tsx:51` · `file-mutation-row.tsx:34`（无 memo）。
流式发布节奏是 animation-frame（`packages/client/ui-conversation/src/client/conversation-nodes/tool.ts:329-331`），
所以 `write_file` / `apply_edit` 长正文写入期间**每帧一次全量 parse**。

**判定（2026-10-22 定稿）**：**纯呈现缺口，无性能项。**
「加增量闭合扫描器取代每帧 parse」这个修法**已撤回** —— 实测分摊到帧是 ~37 µs、0 掉帧，为它引入一个缓存生命周期不变量是负收益。
本条唯一活下来的价值是**呈现**：preparing 行显示不出字段（DSH 的字段级懒读器）。落点即下表 ②，已并入 **U7l**。

| 项 | 改动面 | 验收判据 |
| --- | --- | --- |
| ~~① 闭合检测取代每帧 parse~~ | **不做**（实测无感知的浪费，修法成本高于收益） | — |
| ② 字段级懒读器（呈现）→ 见 **U7l** | 保留 `argsRaw` 供最终渲染（V8 下无成本），只为**展示**增加按字段读取 | bash / run_code 在 preparing 行显示 `description` 前缀；read/write/edit 在 `file_path` 闭合后给可点路径；write/edit 按 1024 字符单位显示内容长度 |

**附带可抄的实测规格**（DSH 用 310 次受控请求测出来的）：只调 `properties` 顺序 **无效**（bash 0/20）；`properties` + `required` **同调**才有效（强制 tool_choice 10/10、pro 自由调用 7/10）；再加一句顺序指令才让 flash 到 19/20。**→ 本仓改 schema DSL 让 `required` 跟着 `properties` 声明序走即可拿到大部分收益，不必烧真 API。**

### A8 · 计时提问的**两次结算** —— P1

DSH `2026-09-19-timed-user-question-two-settlements.zh.md`：超时**结束请求并返回 pending**，但**不丢弃问题** —— 迟到回答通过业务 RPC steer 一条**持久用户消息**。关键约束：Host **只在没有回答 UI 接手时**跑计时器；最后一个接手方离开后**恢复原 deadline**，已过期则立即到期；`remainingMs` 由 Host 计算下发；**投递到传输队列不算接手**。默认 `mode: legacy` 保留阻塞式，显式 `mode: timed` 才带 timeout（配置默认 120 秒），`-1` 回落阻塞。

### U2 · **折叠动画只留一条驱动** —— P0（这是他们踩过的真 bug，我们大概率有同族）

DSH `2026-10-13-chat-single-fold-motion.zh.md` + `2026-10-11-chat-group-tree-exchanges.zh.md`。他们踩到的坑，本仓**结构上更容易踩**：

- **通用折叠路径在折叠发生在读者上方时会留下整屏空白**。DSH 实测的触发来源表：本页有回显的输入正常；**排队消息自动投递 / 另一个标签页发送 / 右侧栏子会话输入框发送 / 子会话被父消息唤醒后人类发送 → 全部整屏空白**，其中一例"补白约 6000 px"。另一例录制的真实 Session：通知在上轮结束后 **13–15 ms** 唤醒新轮次，最小复现空白 **596 px，五秒后仍未恢复**。
- 根因：`ownInput` 只认三种信号（本地回显 `submissionId`、`steeringId`、`lastIsUser`）。**本仓的多入口比 DSH 更多**（IM 网关、A2A、子代理父消息、cron、Goal Round、后台作业、桌面/Web 双壳同会话）—— 每一条**不经过本页对话流回显**的输入都是一次触发。
- 他们的解法：① 「通知不算正文也不算用户消息」，底部从"最后一个 Turn"改成"**最新交互段**"；② 引入 `groupTree: 'exchange' | 'input' | 'turn' | 'process'` **有序位置** + `isAtOrOutside()` 作唯一读取入口；③ 折叠批次走驱动器四步 `begin`（测盒、选落点）/ `prepare`（**写盒之前**先扩补白，避免中间帧被浏览器截断）/ `frame`（**同步**写盒高与 scrollTop）/ `finish`（装最终补白）；④ 批次运行中新起止的折叠/展开行**保持当前尺寸不走自己的过渡**；⑤ **删掉通用路径**（`reserve`/`pendingReserve`/`reserveBelow`/`followAfterFold`）；⑥ `GroupTreeSegments` **按 Turn 增量计数，不扫描已加载节点**。
- 他们还专门解释了"为什么标开头而不是标通知"：Host 认领唤醒输入到写 `user/message` 之间隔了 **187 ms**，只标通知会让新轮**先折后展**。

本仓现状：`groupTree` / `inputFold` / `collapseWhen` → **零命中**。滚动只有 `packages/client/ui-conversation/src/client/chat/ChatView.tsx:808/821-823/876-901` 的直接 `scrollTop` 赋值 + `FOLLOW_THRESHOLD` + 锚点补偿，**没有折叠批次驱动，也没有 prepare 阶段的补白预留**。

**这是本轮性价比最高的 UI 项**：它不是"他们没有的漂亮功能"，而是**已经发生过的用户可见故障 + 完整根因分析 + 已被验证的修法**，连复现矩阵（`apps/web/tests/fold-blank-matrix.e2e.ts`）都给出来了。

**验收**：① 本仓复刻 fold-blank 矩阵（IM 投递 / 另一标签页 / 侧栏子会话 / 父消息唤醒）全部无空白；② 只有一条折叠驱动；③ 通知唤醒的 Turn 不折叠上一交互段；④ 减少动态效果时折叠行立即完成。
